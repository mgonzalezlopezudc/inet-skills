## 1  Effectiveness — does each skill make the agent produce correct work?

### What works well

| Aspect | Evidence |
|--------|----------|
| **Pre-write contract discipline** | `inet-code-authoring` forces a structured contract (invariant, owner, entry point, siblings, boundaries, verification) before the first edit. This directly attacks the #1 class of agent bugs: writing code against a wrong mental model. The self-audit checklist closes the loop. |
| **Layered review checks** | `inet-code-review` carries ~87 KB of structured, layer-indexed `RP-*` investigation prompts across General C++, OMNeT++, INET, and IEEE 802.11. Context-budget tiers prevent context exhaustion on large diffs. |
| **Evidence hierarchy for disputes** | `inet-agent-orchestration` §Dispute Escalation codifies `runtime evidence > captures > config > source > hypothesis`. This prevents agents from "out-reasoning" a debugger. |
| **Forensic branch management** | `inet-branch-cleanup` and `inet-branch-rebase` are remarkably thorough: coverage ledgers, immutable attempt branches, opp_repl oracle contracts, checkpoint-and-resume logbooks. They make destructive history rewrites auditable. |
| **Seal enforcement** | `inet-architectural-requirements` wires into the canonical seal registry, making it hard for an agent to silently modify frozen code. |
| **Standards traceability** | `ieee80211-standards` + the walkthrough writer + the 802.11 review layer form a chain from normative text → implementation → documented evidence. |

### Gaps

| Gap | Impact |
|-----|--------|
| **No runtime-feedback loop** | Skills tell the agent *what* to run, but no skill parses CI/test output and feeds structured pass/fail/flaky status back into the orchestrator's gate logic. The agent must interpret raw text. |
| **Review checks are read-only text** | The ~87 KB of review references are prose; they cannot be mechanically queried or filtered. An agent either reads all or guesses which subset matters. |
| **No refactoring skill** | `inet-code-authoring` covers fixes/features; large-scale mechanical refactors (renames across 200 files, API migration) have no dedicated workflow, especially around baseline management. |
| **Missing performance/scalability skill** | No skill addresses simulation performance profiling, memory diagnostics, or scalability regression. |

## 2  Efficiency — how much agent context/time does each skill consume?

### Efficient

- **Compact operational skills** (8–55 lines): `inet-simulation-run`, `inet-ned-ini-analysis`, `inet-fingerprint-regression`, `omnetpp-result-plotting` are lean. They give one command pattern, one workflow, and get out of the way.
- **Layered loading** in `inet-code-review`: context-budget tiers explicitly say "small diff → load 1 layer; large diff → load on demand." This is unusually self-aware for an AI skill.
- **Delegation depth limit** in `inet-agent-orchestration`: "Keep depth at one; specialists must not delegate" prevents recursive sub-agent chains.

### Costly

| Concern | Skill(s) | Cost |
|---------|----------|------|
| `inet-branch-rebase` is 228 lines of dense procedure | `inet-branch-rebase` | A single skill consumes ~14 KB of context. With its two reference docs, it's ~25 KB before the agent touches a single file. |
| Review references are large and overlapping | `inet-code-review` refs | ~87 KB total. Even with tiered loading, a medium diff (100–500 lines) may need 3 layer refs ≈ 27 KB, plus the SKILL.md, plus the canonical guide. |
| Orchestration + authoring + review triple-loads shared references | `inet-agent-orchestration`, `inet-code-authoring`, `inet-code-review` | `common-agent-pitfalls.md` is referenced by both authoring and review. The review layer refs are shared. In a full orchestrated change, the same conceptual checks may enter context 2–3 times. |
| `inet-branch-cleanup` and `inet-branch-rebase` share ~80% of their contract structure | Both | Two 130+ line and 228-line skills with overlapping opp_repl, state-log, and coverage-ledger contracts. |

## 3  Utility — how often and broadly is each skill applicable?

### High utility (used on nearly every task)

| Tier | Skills |
|------|--------|
| **Every change** | `inet-code-authoring`, `inet-architectural-requirements`, `inet-simulation-run`, `inet-build-debug-modes` |
| **Every review** | `inet-code-review`, `inet-pull-request-authoring` |
| **Every debug session** | `inet-cmdenv-log-analysis`, `inet-ned-ini-analysis` |

### Medium utility (used when applicable)

`inet-fingerprint-regression`, `inet-unit-tests`, `inet-pcap-tshark-analysis`, `omnetpp-result-analysis`, `omnetpp-result-plotting`, `inet-80211-packet-debugging`, `inet-packet-tag-debugging`, `ieee80211-standards`

### Low utility (rare tasks)

| Skill | Why rare |
|-------|----------|
| `inet-branch-cleanup` | Only when a user explicitly asks to reconstruct history — not every PR |
| `inet-branch-rebase` | Only for high-risk rebases across changed upstream — maybe once per release cycle |
| `inet-80211-walkthrough-writer` | Only when writing showcase documentation for a Wi-Fi feature |
| `inet-agent-orchestration` | Only in multi-agent sessions; in single-agent mode it's mostly guidance to skip |

### Questionable utility (external)

The **SecureCoder plugin** (8 skills) targets web-application security (XSS, SQL injection, session management). INET is a C++ discrete-event simulation framework with no web surface, no databases, no user sessions. These skills have essentially **zero applicability** to this workspace and consume discovery/routing overhead on every invocation.

## 4  SWOT Analysis

### Strengths

1. **Extremely deep domain encoding.** The skill set captures institutional knowledge that would take a human months to learn: opp_repl oracle contracts, fingerprint test semantics, INET packet-tag lifecycle, IEEE 802.11 normative traceability, seal policy. This is a genuine competitive moat against generic AI agents.

2. **Principled separation of concerns.** Authoring ≠ Review ≠ Architecture ≠ PR structure. Each skill has a clear owner and explicitly states what it does *not* do. Cross-skill routing is documented in tables.

3. **Evidence-first culture.** Nearly every skill demands reproducible evidence before conclusions: debug-mode runs, specific seeds, explicit filters, source-backed contract fields. The "no TBD, no placeholder" rule in the authoring contract is a strong anti-hallucination measure.

4. **Graduated escalation.** The debugging skills form a clear ladder: NED/INI analysis → Cmdenv logs → PCAP/TShark → event logs → LLDB. Each skill says when to escalate to the next.

5. **Self-documenting workflow.** The branch-management skills produce durable logbooks, coverage ledgers, and checkpoint branches. Work can be resumed across sessions or handed off between agents.

### Weaknesses

1. **Onboarding cliff.** A new agent or human contributor faces 23 skills + 10 review references + the full `doc/project/` hierarchy. There is no "beginner mode" or progressive disclosure. The first task always costs a full policy read.

2. **Context budget pressure.** A full orchestrated 802.11 change could load: orchestration (10 KB) + authoring (10 KB) + 802.11 review checks (7 KB) + INET review checks (9 KB) + OMNeT++ review checks (9 KB) + common pitfalls (6 KB) + architectural requirements (7 KB) + standards (2 KB) + the canonical `doc/project/` rules ≈ **70+ KB of instructions** before any source code enters context. This is a material fraction of most models' effective working memory.

3. **Overlap and redundancy.** `inet-branch-cleanup` and `inet-branch-rebase` share state-log, opp-repl-contract, and coverage-ledger patterns but are separate 130/228-line documents. The review layer references are loaded by both `inet-code-authoring` and `inet-code-review`, meaning shared references like `common-agent-pitfalls.md` may enter context twice.

4. **No feedback automation.** Skills prescribe what to run but don't parse structured output. The agent must read raw test/build/lint output and decide pass/fail, which is error-prone for fingerprint hashes, large log files, or flaky tests.

5. **802.11 overrepresentation.** 6 of 23 skills (26%) plus one dedicated domain rule focus exclusively on IEEE 802.11. While INET covers dozens of protocol families (IPv4/6, TCP, UDP, OSPF, BGP, Ethernet, LTE, etc.), none of those has a single dedicated skill.

### Opportunities

1. **Structured test-result parsing.** A skill or script that parses `opp_repl`, fingerprint, and unit-test output into structured JSON (pass/fail/expected-change/flaky) would eliminate a large class of agent misinterpretation and enable automated gate decisions.

2. **Skill composition / meta-loading.** A lightweight registry that tells the orchestrator "for this diff touching `src/inet/linklayer/ieee80211/`, load skills X, Y, Z and skip A, B, C" would reduce context waste. This could be a JSON file mapping path globs to skill subsets.

3. **Protocol-family skill templates.** The 802.11 skill pattern (standards ↔ review checks ↔ regression ↔ packet debugging) could be templated for TCP/IP, Ethernet, OSPF, etc. This wouldn't need to be as deep, but even a lightweight "inet-tcp-review-checks.md" would prevent the agent from treating TCP changes as generic C++.

4. **Refactoring / migration skill.** Large-scale renames, API migrations, and deprecation campaigns are a recurring INET need (e.g., the chunk API evolution). A dedicated skill with rename-verification and baseline-update workflows would reduce manual effort.

5. **CI/CD integration skill.** A skill that knows how to interpret GitHub Actions / Jenkins output, map failures to changed files, and decide "retry vs. investigate vs. expected" would close the loop between code authoring and verification.

6. **Consolidation of branch-management skills.** The shared infrastructure (state-log, opp-repl-contract, coverage ledger) could be factored into a shared reference, with `inet-branch-cleanup` and `inet-branch-rebase` becoming thinner workflow-specific skins.

### Threats

1. **Context-window starvation.** As the skill set grows, the total instructional load risks exceeding model working memory, causing the agent to silently drop rules or hallucinate simplified procedures. The review references are already at ~87 KB.

2. **Staleness.** Skills reference specific files (`examples/ieee80211/analysis/wifi_analysis.py`, `doc/project/enforcement/check-source-seals.sh`). If the codebase moves these without updating the skills, the agent will fail at runtime with confusing errors.

3. **Over-proceduralisation.** The branch-cleanup and branch-rebase skills are so detailed that an agent may follow them mechanically without understanding *why*. A single misinterpretation of "coverage ledger" or "replay manifest" can cascade through dozens of steps.

4. **Model capability assumptions.** The skills assume the agent can reliably maintain a coverage ledger across 20+ commits, parse raw LLDB backtraces, interpret fingerprint hashes, and keep multi-agent delegation graphs consistent. Current models sometimes fail at simpler tasks.

5. **SecureCoder noise.** The 8 security-plugin skills are always loaded, always discovered, and never applicable. They add routing overhead and, worse, their mandatory-secure-web-skills rule claims to apply to "ALL code generation" — which could cause an agent to waste context on web-security checks for C++ simulation code.

## 5  Recommendations

### Remove or suppress

| Action | Target | Rationale |
|--------|--------|-----------|
| **Suppress for this workspace** | All 8 SecureCoder skills | Zero applicability to a C++ simulation framework. They add discovery noise and the `mandatory-secure-web-skills` claim conflicts with the domain. Disable via workspace-scoped plugin override or `mcp_config.json`. |

### Add

| Priority | Proposed skill | Purpose |
|----------|---------------|---------|
| **High** | `inet-test-result-parser` | Parse `opp_repl`, fingerprint, and unit-test output into structured JSON. Gate decisions become mechanical, not interpretive. Include a script, not just prose. |
| **High** | `inet-skill-selector` | A JSON or YAML registry mapping path globs and change types to recommended skill subsets. Reduces cold-start context by ~40%. |
| **Medium** | `inet-refactoring` | Workflow for large-scale mechanical changes (API migration, rename, deprecation). Covers baseline-update strategy, incremental verification, and ripple-effect tracking. |
| **Medium** | `inet-tcp-ip-review-checks` | Lightweight review checks for the TCP/IP, UDP, SCTP, IPv4/6 stacks. Even 3 KB of domain-specific investigation prompts would outperform generic C++ checks. |
| **Low** | `inet-ci-integration` | Interpret CI pipeline output, map failures to files, classify retry/investigate/expected. |
| **Low** | `inet-performance-profiling` | Simulation performance diagnostics: valgrind/callgrind, memory, scalability regression detection. |

### Refactor

| Action | Skills | Benefit |
|--------|--------|---------|
| Extract shared branch-management infrastructure into a common reference | `inet-branch-cleanup` + `inet-branch-rebase` | Eliminate ~8 KB of duplication. Each skill becomes a thinner workflow shell over shared contracts. |
| Merge `omnetpp-result-analysis` and `omnetpp-result-plotting` | Both | They're almost always used together. A merged skill with an "extract → plot" workflow would be more natural and save one skill-routing decision. |
| Add a "quick-start" section to `inet-agent-orchestration` | Orchestration | A 10-line "for a single-agent session, just use authoring + the applicable tool skill" summary would save context for the 80% case. |

### Harden

| Action | Scope | Benefit |
|--------|-------|---------|
| Add path-existence assertions at the top of every skill that references specific files | All skills | A `[ -f ... ] || echo "SKILL ERROR: expected file missing"` guard prevents cascading confusion when the repo evolves. |
| Version-stamp each skill with the last `doc/project/` revision it was audited against | All skills | Makes staleness detectable. A mismatch triggers a skill refresh rather than silent divergence. |

## Summary scorecard

| Dimension | Score | Notes |
|-----------|-------|-------|
| **Effectiveness** | ★★★★☆ | Excellent domain encoding and evidence discipline; weakened by lack of automated feedback parsing and protocol-family imbalance |
| **Efficiency** | ★★★☆☆ | Compact operational skills are good; heavyweight review/branch skills risk context saturation; redundancy between cleanup/rebase and authoring/review |
| **Utility** | ★★★★☆ | Core workflow skills are high-utility; branch-management and walkthrough skills are situational but justified; SecureCoder is pure overhead |
| **Overall design quality** | ★★★★☆ | One of the most thoughtful AI-agent skill sets I've seen for a complex codebase. The main risks are growth-related: context pressure, staleness, and diminishing returns from over-proceduralisation |
